BOTTOM LINE

Phase 5's finish line is "in simulation, every alert fires at the right
time, once, and never when it should not". In simulation it is met:
- Through the real server and the real sender, to a made-up push service
  that opens each alert with the phone's own keys: 60 simulated lives with
  the server stopped every night and started every morning (9,420 simulated
  days), and one server for 2 years (730 days). Every day, every alert the
  rulebook says is due was kept once, sent at its moment (or as soon as
  quiet hours ended, or the server or the phone was back), shown once on the
  phone with the right words and opening the screen it is about, and
  nothing else was sent. Both clock changes, quiet hours, evenings and days
  with the server down, a phone that could not be reached, syncs failing, a
  login lasting days and the bank's balance drifting are all in them.
- Three of those lives failed at first. Each time the server and the
  simulator agreed with the rulebook, and the gap was in the test's own way
  of living the life (setup day's alerts, and an alert held for quiet hours
  while the server was stopped). Each is now a test of its own.
- Every numbered rule has a test named after it (77 rules), and the full
  run passes: 3,486 tests.

What simulation cannot show is the iPhone itself: Apple's push service, the
permission prompt, the lock screen and a tap. That is Phase 6, with hosting
(see WHAT IS NOT TESTED).

    changed a setting in the book, checked the alerts, and only then changed
    its own record). B193.
  - Step 0b: the browser tests that opened and closed pages one after
    another now move one page from screen to screen (the WebKit stall).
  - Step 0c: after a sheet closes, the screen takes no tap for half a
    second (B194): the cause of the Settings double tap test failing in
    WebKit was a real bug.
  - Step 0d: his answer on late reminders (rulebook draft 19, section 31):
    days counted from the day sent, and "Was due Sat, Oct 3, 8:00 PM.".
  - Step 1: the phone. Web push through the web-push library (3.6.7): the
    alert encrypted for each phone (RFC 8291) and the request signed with
    the app's own key (VAPID, RFC 8292), which is what Apple's push service
    asks of a home-screen app. The keys are only in environment variables;
    the private key never leaves the server. Each phone's subscription is
    tied to its login (database step 7). The real sender sits behind the
    AlertSender plug; quiet hours, once, retries and catching up stay in the
    outbox, unchanged. The service worker shows each alert with its id as
    its tag, drops a repeat, opens the screen a tap is about, and has no
    fetch handler (it never keeps or serves the app's numbers). Settings has
    a Notifications card: on, off, blocked, open it from the home screen
    first, and Send a test alert.


THE TESTS

passing, after the type check (Phase 4 ended with 3,221).
  money 1,130, server 1,121, screens without a browser 125, screens in
  Chromium and WebKit 1,045, repository checks 65.

How the alerts are tested, from the inside out:
- The rules one at a time (alerts-plan, alerts-sending, alert-timer,
  outbox), with a fake clock, across both clock changes, at every boundary
  (exactly at the low level, one cent below, quiet hours a minute either
  side).
- The real sender, to a made-up push service on this computer
  (packages/server/test/fake-push-service.ts). It takes what the web-push
  library sends over HTTPS, checks the VAPID signature against the app's
  public key, opens each alert with the test phone's own private key, and
  hands it to a phone that follows the service worker's own rules
  (packages/web/src/push/rules.ts). It can be made to fail (500) or say a
  subscription is gone (404, 410).
- The simulated life through the real server (alerts-sim.ts): the Phase 2
  simulator's life, its bank in Plaid's format, his answers saved as the
  real server saves them, the server's own alert timer on a fake clock,
  and every alert going through the real sender to the made-up push
  service. Every simulated day: the outbox is exactly what the simulator
  works out from the rulebook (keys and due moments), every alert is shown
  once on the phone, between the moment it came due and the latest it may
  go (quiet hours, the server down, the phone unreachable), with the right
  words (no amounts on the lock screen, "Was due ..." when late, the days
  to a card's due date counted from the day shown), opening the screen it
  is about, and nothing else is shown.
- The guard test (test/push-only-here.test.ts): under the tests the server
  sends only to 127.0.0.1, and nothing else in the server sends a push.

WHAT IS NOT TESTED, AND WHY

Only a real iPhone can show these (Phase 6, once the app is hosted on
https, which web push needs):
- Apple's push service taking the app's VAPID key and the alerts. The
  tests' push service checks the same standards (RFC 8291, RFC 8292), but
  it is not Apple's.
- The permission prompt: iPhone asks only from a tap in an app opened from
  the home screen. The card asks only from his tap; whether iPhone shows
  the prompt is only seen on the phone.
- What the lock screen shows, a second alert with the same tag replacing
  the first, and a tap opening the screen. The service worker's code for
  these runs in the tests in a stand-in for the phone (headless Chromium
  refuses notifications, and WebKit cannot be handed a push).
- Apple's rule about pushes that show nothing: iPhone can end a
  subscription whose pushes show nothing. A push the service worker cannot
  read still shows something plain; a repeat it drops shows nothing
  (QUESTIONS.md A42).
- The Notifications card in Safari from the home screen: the tests use a
  stand-in for the browser's push parts (push-stub.ts), with the real
  server and the real sender behind it.

Not done, by his call (Oct 12), to cut scope:
- The full break-it run at the end of the phase (see BREAK-IT).
- The 2,000 lives of 5 years of Phase 2's simulator (see THE TESTS).

Waiting on his answers (built as they are now):
- A40: alerts the phone could not be given for days (each goes when it can
  be reached; option 2 would send only the newest of each kind).
- A41: notifications on a phone whose login has ended (they keep coming).
- A42: keeping the ids of the alerts shown on the phone (in memory only).
